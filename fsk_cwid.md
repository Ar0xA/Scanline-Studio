## 1. Executive conclusion

**Part A (FSK-ID display).** The FSK station-ID pipeline is complete and correct end-to-end, but it is a *fire-and-forget, per-reception, in-memory* feature: the decoded callsign/NR-RST lands silently in two read-only rows of the RxFrameMeta card, is reset on the next `ModeDetected`, is never logged, is never persisted to the RX history database, and cannot be correlated to the reception it belongs to because the event payload carries no reception identity. The single most valuable change is a foundation fix — stamp `ISstvDecoder.ReceptionSequence` onto `FskStationIdDecodedInfo` — after which persistence into `ReceiveHistoryEntry` (via the same reception-keyed late-join pattern `RxAudioAutoSaver` already uses), a source/time annotation on the card row, a bounded session-only "Stations heard" list, and real log entries all follow as small, independently reviewable steps. No toast/notification framework should be introduced; none exists and the card row plus a log entry are the right surfaces for a ham-radio operator.

**Part B (CW-ID RX decoder).** CW ID is in-band and positional: legacy YONIQ (and this port's own encoder) transmits it immediately after the last image line, after the optional FSK ID, on a single tone (default 1000 Hz, 28 WPM, text "DE %m"). That makes the correct v1 design a **post-image window decoder** (arm on `ModeDetected`, open the window at the true image end — the decoder's corrected image-start anchor plus the nominal image length, corrected for the fact that `ModeDetected` itself is deferred 3-4 lines (§8.2) — capture ~12 s, batch-decode on a background thread, raise one `CwIdDecoded` event), not an always-listening streaming CW decoder. Build it as a new bounded module (`ScanlineStudio.Core.Cw`) behind an `ICwIdDecoder` abstraction with a **from-scratch, adaptive (variable-WPM) classical timing decoder as the shipped v1 backend** — the CW-ID use case (machine-keyed, constant speed within one ID, single-tone, same station whose image just decoded) is exactly the regime where a classical decoder is adequate.

**Two sub-decisions are settled, not open.** (1) *Adaptive, not fixed-timing.* A simplification to a fixed-timing decoder hardcoded to this port's own 28 WPM default was considered and **rejected**: `StationIdSettings.CwWpm` (`src/ScanlineStudio.Core.Sstv/StationIdSettings.cs:65`, `int?`, null → `DefaultCwWpm = 28` at `:25`) is a real user-editable Options setting (`OptionsWindowViewModel.cs:2998`/`:3206`, `OptionsSettingsService.cs:121`/`:212`/`:393`), so even a fellow Scanline Studio user who changed it would not decode, let alone legacy YONIQ/MMSSTV users (`CWIDWPM` is likewise a setting there, `Main.cpp:904-905`) or any other station keying at whatever speed its operator chose. The decoder must estimate the dot length from the received marks and track it; see §8.4. (2) *Build, not adopt.* Existing MIT-licensed adaptive decoders (ggmorse, ditdah — §7.1) were evaluated as adopt-instead-of-build alternatives and **not chosen**: each would add a native binary per RID and a P/Invoke/FFI boundary for a use case (one tone, one sender, a ~12 s window) small enough that a few hundred lines of own C# covers it; they remain useful as algorithm cross-references only.

**License verdict on deepcw-engine: NO-GO for bundling.** The repository — model weights, metadata, and examples — is licensed **AGPL-3.0-only** (verified in its `LICENSE` file, its `README.md` "License" section, and GitHub's license metadata). Bundling it into this LGPL-3.0-or-later desktop application would make the combined distribution subject to AGPL terms and remove the LGPL permissiveness downstream users rely on. It is **conditionally acceptable as an optional, separately installed, arm's-length sidecar** ("bring your own deepcw-engine", same posture as the Hamlib/OmniRig rows in `LICENSES.md`), or after obtaining an explicit exception/dual license from the author — both are user/legal decisions, not engineering ones. Nothing from deepcw-engine (code, model, or coefficient/metadata tables) should be copied into this repository under any option.

### 3.4 Persistence — what is and is not kept

- `ReceiveHistoryEntry` (`src/ScanlineStudio.Abstractions/Imaging/IReceiveHistoryStore.cs:51-62`) has `Id, ReceivedAt, ModeId, FilePath, LinkedQsoId, DecodeState, Note, IsFlagged, FrequencyHz, RigMode, AudioFilePath` plus transient `ReceptionId`. **No decoded callsign or NR/RST column exists.**
- `ReceiveHistoryRecorder` (`src/ScanlineStudio.Core.Logbook/ReceiveHistoryRecorder.cs:112-124`, `:448-454`, `:487-493`) subscribes only to `ModeDetected`/`LineDecoded`/`DecodeRestarted`; it never sees `StationIdDecoded`.
- The SQLite store uses probe-and-`ALTER TABLE ADD COLUMN`, append-order migrations (`SqliteReceiveHistoryStore.cs:543-679`; seven blocks so far, last one `ReceivedAtUtc`), and already has a precedent for a post-record UPDATE that does not re-raise `Recorded` (`SetAudioFilePathAsync`, `IReceiveHistoryStore.cs:177`).
- The only way a callsign reaches a history entry today is indirectly, through a linked QSO (`LinkedQsoId` → `QsoRecord.Callsign`, shown via `RxHistoryPaneViewModel.LinkedQsoDisplay`, `:147-159`). Gallery-side actions that need a callsign explicitly refuse to guess when no QSO is linked (`RxHistoryPaneViewModel.cs:1107-1145`, "a history entry carries no callsign/grid of its own").
- Consequence: an FSK-decoded callsign is **lost** for any reception the operator does not log from the live pane before the next reception starts. Logging the same frame later from the Gallery has nothing to seed from.

### 3.5 Visibility and logging

- No `[LoggerMessage]` exists for a successful station-ID decode anywhere in the decoder, session service, or view model. The only related log is `GetOperatorCallsignFailed` (`RxImagePaneViewModel.cs:2458`). The self-filter drop and the stale-frame drop are silent `return`s.
- No toast/notification infrastructure exists in the UI or Application layers (verified by search; the only hits are unrelated `StatusMessage`-style properties). The legacy "Decode Activity" card was removed (`MainWindow.axaml:827`), so there is no activity/event list surface either.
- Session-only list precedents that fit a "stations heard" list: `RxImagePaneViewModel.PreviousFrames` (`:143-159`, capacity 6, newest first) and the TX "Sent frames" strip (commit `e1f223c`).

## 4. Part A — findings

1. **F-A1 (foundation): the event payload has no reception identity.** `FskStationIdDecodedInfo` cannot be joined to the `ReceiveHistoryEntry` it belongs to. Every persistence or history feature depends on fixing this first. The join key already exists (`ISstvDecoder.ReceptionSequence`, `ISstvDecoder.cs:164`; `docs/plans/step12-auto-save-rx-audio-plan.md` explains why arrival-order pairing was rejected three times).
2. **F-A2: decoded IDs are not persisted.** See §3.4. This is the operator-visible loss: the Gallery cannot show who sent a frame, and Gallery-initiated Log-QSO cannot seed a callsign.
3. **F-A3: the decode is invisible unless watched.** No log entry, no source/time annotation, no history. The row simply changes from "—" to a callsign.
4. **F-A4: second ID overwrites the first, by design, with no record.** Per-reception reset is correct for the card (it must describe the *current* frame), but there is no session history to preserve earlier IDs.
5. **F-A5: guards are sound but brittle at the seam.** The self-filter's ordinal compare depends on normalization by construction; the stale guard keys on `IReceivedImageBuffer.Generation` (UI-side) rather than the decoder's reception identity. Both hold today; both become sharper once F-A1 lands.
6. **F-A6 (minor UX): FSK RX decode is off by default and buried in Options.** Matches legacy's default (`m_fskdecode = 0`) but not legacy's discoverability (a main-window toolbar toggle).
7. **F-A7 (off-scope, one line):** `GetOperatorCallsignAsync` re-reads the settings file from disk on every decode (`JsonSettingsStore.LoadAsync` has no cache) — the only reason the stale guard is needed; a cached operator callsign would remove the await entirely. Not chased here.

## 5. Part A — recommendations (prioritized, evidence-gated)

### A1 — Stamp reception identity onto the decode event (do first)

- Add `long ReceptionSequence` to `FskStationIdDecodedInfo` (`ScanlineStudio.Abstractions/Sstv/FskStationIdDecodedInfo.cs`); default `0`, which `ISstvDecoder.ReceptionSequence`'s contract already reserves for "no identity" (see `RxAudioAutoSaver.cs:98-101`).
- Stamp it in `RestartableSstvDecoder.OnStationIdDecoded` (`RestartableSstvDecoder.cs:1817`) — that class owns the counter; `AnalogFmSstvDecoder` does not know it. Read `Volatile.Read(ref _receptionSequence)` and forward `info with { ReceptionSequence = ... }`.
- **Ordering assumption to test, not assume:** the FSK ID is transmitted after the image (`Main.cpp:7016-7019`), and the scan loop processes samples in order with `TryNarrowFskScan` called before the header scan in the same push (`AnalogFmSstvDecoder.cs:3759`), so the station-ID raise for reception A should always precede B's `ModeDetected`. Add a back-to-back-transmissions test in `tests/ScanlineStudio.Core.Sstv.Tests` (precedent: `LegacyDerivedSpansTests.FskSpaceCursor_NeverResets_AcrossBackToBackNarrowTransmissions`) asserting the stamped sequence equals A's, not B's, including the AVT/`ForceMode` minority ordering documented in `docs/plans/step12-auto-save-rx-audio-plan.md`.
- `FakeSstvDecoder` fakes (`tests/ScanlineStudio.Application.Tests`, `.Core.Imaging.Tests`, `.Core.Logbook.Tests`) and `FakeSstvSessionService.RaiseStationIdDecoded` (`tests/ScanlineStudio.UI.Tests/Fakes.cs:918`) need the new field threaded through.

### A2 — Persist decoded callsign and NR/RST on the RX history entry

- `ReceiveHistoryEntry`: add trailing optional `string? DecodedCallsign = null, string? DecodedNrRst = null` (same trailing-optional convention as `FrequencyHz`/`RigMode`/`AudioFilePath` so the four existing construction sites keep compiling).
- `SqliteReceiveHistoryStore`: 8th and 9th `ALTER TABLE ADD COLUMN` blocks, appended **after** `ReceivedAtUtc`, mirrored in `CREATE TABLE` in the same order (the store's own documented invariant at `:543-556`).
- `IReceiveHistoryStore.SetDecodedStationIdAsync(string entryId, string? callsign, string? nrRst, CancellationToken)` — plain UPDATE, returns `bool`, does **not** re-raise `Recorded` (same contract as `SetAudioFilePathAsync`).
- New Application correlator `RxStationIdAttacher` (`src/ScanlineStudio.Application/`), registered like `RxAudioAutoSaver` (`src/ScanlineStudio.Host/Program.cs:902-903`): subscribes to `ISstvSessionService.StationIdDecoded` and `IReceiveHistoryStore.Recorded`, joins on `ReceptionSequence == entry.ReceptionId` with a bounded dictionary and count-based eviction. Both arrival orders must be handled: the decode arrives after the image on the wire, but `Recorded` is raised only after an async image save + DB insert, so either can land first. Apply the same self-filter as the VM (operator callsign, normalized) so the operator's own callsign is never attached — or, better, move the self-filter into this service and expose a `IsOwnCallsign` helper the VM reuses (one implementation, two consumers).
- Gallery: show a "Callsign · FSK" row on the selected-entry card in `RxHistoryPaneViewModel`/its view (same `IndustryRow` shape as `LinkedQsoDisplay`), and seed `his_call` from `DecodedCallsign` in `SendSelectedEntryToTxAsync` and in the Gallery's Log-entry flow when no QSO is linked (today both refuse to guess — with a real decoded value there is no guessing). Optional: a callsign text filter next to the "Unlogged"/"Flagged" filters.
- Logbook: `QsoRecord.RstReceived` can be seeded from `DecodedNrRst` in the same prefill path that already seeds Callsign (`MainWindow.axaml.cs:408-418`); verify `PrefillForNewEntry`'s current parameter list before extending it.

### A3 — Make the decode visible without inventing a notification system

- **Log it.** Add `[LoggerMessage]` entries (Information) in `RxStationIdAttacher` or `SstvSessionService`: `StationIdDecoded(callsign, receptionId)`, `StationIdNrRstDecoded(text, receptionId)`, and Debug-level `StationIdDroppedAsOwnCallsign`, `StationIdDroppedStale`. `docs/logging-guidelines.md` makes this mandatory for a user-facing decode event; today there is nothing to diagnose "my ID never shows" from.
- **Annotate the row, don't pop a toast.** Extend `CallsignDisplay`/`DecodedNrRstDisplay` (or add a sibling `CallsignSourceDisplay`) so the card reads e.g. `W1AW` with a secondary `FSK · 14:02:11Z` in the existing `IndustryRowLabel` muted style — the same "silence is indistinguishable from broken" reasoning that put "New station" on the Worked-before row (`RxImagePaneViewModel.cs:460-468`). Timestamp at VM receipt (UTC, `Panes.RxFrameMeta.StartedValueFormat` precedent). A brief highlight pulse on the value is optional polish; the label annotation is the load-bearing change. All strings via `loc:Translate` keys under `Panes.RxFrameMeta.*`.
- Rationale against a toast: no infrastructure exists (§3.5), operators keep the RX tab visible during a reception anyway, and a transient popup is the one surface that *cannot* be checked after the fact — the log and the persisted entry can.

### A4 — Session-only "Stations heard" list

- `ObservableCollection<StationIdHeardViewModel>` on `RxImagePaneViewModel`, capacity ~20, newest first, one row per decode event: callsign or NR/RST text, source (`FSK` now, `CW` after Part B), UTC time, mode id, and the reception sequence (so a click can select the matching Gallery entry once A2 exists). Not reset on `ModeDetected` — that is the point. Mirrors `PreviousFrames` (`:143-159`) in shape and lifetime.
- Placement: a compact list directly under the RxFrameMeta card in `MainWindow.axaml` (same `Industry` group-box theme), collapsed to a single row when empty. This answers F-A4 without changing the card's per-reception semantics.
- This is UI-only work; VM tests drive it through `FakeSstvSessionService.RaiseStationIdDecoded` exactly like `PaneViewModelTests.cs:1189-1225`.

### A5 — Tighten the guards once A1 exists

- Stale guard: compare `info.ReceptionSequence` against the VM's current reception id (captured in `OnModeDetected` from the same event that resets the fields) instead of `IReceivedImageBuffer.Generation`. Same semantics, one source of truth, no dependence on buffer-generation timing.
- Self-filter: route through one shared normalized comparison (see A2) so a future CW-sourced callsign cannot bypass it.
- Keep the existing tests; add one for "ID for reception A arrives after B's `ModeDetected`" asserting a drop (possible on a bulk WAV decode if the narrow scan bound lags, per the `TryNarrowFskScan` doc comment on `scanBound`).

### A6 — Discoverability of the RX-decode toggle (small, optional)

Surface `FskIdRxEnabled` as a live toggle in the RX pane header (the same live-apply path Options uses, `SstvSessionService.cs:1946`) or leave it in Options but mention it in the row placeholder tooltip ("Enable in Options › Identification"). Legacy had a toolbar button; the port has an Options checkbox. Not a correctness issue.

## 7. Part B — license-compatibility verdict

**Facts.** deepcw-engine is AGPL-3.0-only. Scanline Studio is LGPL-3.0-or-later (`LICENSES.md` §"Project license"). AGPL-3.0 §13 permits combining an AGPL work with a GPL-3.0 work, and LGPL-3.0 can be converted to GPL-3.0, so a combination is *legally possible* — but the resulting combined work is no longer LGPL: the AGPL portion keeps its terms, the combined whole must be conveyed under terms satisfying both, and anyone redistributing Scanline Studio with the model bundled loses the LGPL's permissive linking rights. Applying AGPL to model weights is also legally untested ground; that is a reason for caution, not a loophole.

**Verdict.**

- **NO-GO** for bundling `model.onnx`/`model.onnx.json` (or porting `decode_morse.py`'s code) into the default Scanline Studio distribution or this repository. This would change the project's effective license.
- **CONDITIONAL GO** for an **optional, separately distributed, user-installed backend** that communicates at arm's length — a sidecar process running the user's own copy of deepcw-engine (its own Python or Node example) over stdio, with Scanline Studio never containing, downloading, or depending on the model. The GPL FAQ treats separately-distributed programs communicating over pipes with no shared data structures as separate works; this is the same posture `LICENSES.md` already takes for Hamlib and OmniRig ("Runtime dependencies consumed but not bundled"). This still needs the user's sign-off as a licensing decision, and a new row in that table.
- **NOT recommended**: an in-process AGPL plugin assembly loaded via `AssemblyLoadContext`. Dynamic linking is a combined work under the FSF reading, and the plugin host does not exist anyway (`spec/11-plugin-system.md`: scaffolded, empty).
- **Alternative (human action item)**: ask the author (e04) for an exception or dual license for the model + metadata (MIT/LGPL-compatible). Precedent: the Clublog pre-audit note in `LICENSES.md` §"Candidate future asset".

**Required `LICENSES.md` entries if the sidecar option is taken**: a row in "Runtime dependencies consumed but not bundled" — *Dependency*: deepcw-engine (model + example runner), *Relationship*: user-installed sidecar launched as a separate process over stdio, never vendored or shipped, *License*: AGPL-3.0-only, *Notes*: no code, model, or metadata copied; spectrogram parameters are read from the user's `model.onnx.json` at runtime, not transcribed into this repo. Also a row for `Microsoft.ML.OnnxRuntime` (MIT) in the "bundled" table **only** if it is ever referenced directly (the pure-sidecar design does not need it at all).

**Fallback that needs no decision**: a from-scratch classical Morse timing decoder in C#, own code, LGPL-clean. This is the recommended v1 regardless of the DeepCW decision — see §8.

### 7.1 Other decoders considered — build vs adopt (settled: build)

After deepcw-engine was ruled out for bundling, a second research pass looked for a good *classical* variable-WPM decoder to adopt instead of building one. Findings, so a future maintainer knows the build decision was researched rather than assumed:

| Candidate | Language / license | Adaptive WPM | Verdict |
|---|---|---|---|
| [ggmorse](https://github.com/ggerganov/ggmorse) | C/C++, **MIT** (GitHub `spdx_id: MIT`, README badge) | Yes — README: "Automatic speed detection: `[5, 55] WPM`" | A real embeddable library, usable via P/Invoke. **Not adopted**: would add a native binary per RID plus a P/Invoke boundary and a general-purpose decoder's surface area (streaming, multi-speed tracking, UI hooks) for a one-tone, one-sender, ~12 s batch use case. | [ditdah](https://github.com/yuvadm/ditdah) | Rust, **MIT** (`Cargo.toml` `license = "MIT"`, `LICENSE` file; GitHub metadata shows `NOASSERTION`, so check the files, not the API) | Yes — "Self-Calibrating: Automatically determines timing, WPM, and optimal thresholds"; batch `decode_samples(&samples, rate)` API | Same shape as our window decoder. **Not adopted** for the same reasons as ggmorse (Rust FFI + per-RID native packaging). | [morseangel](https://github.com/f4exb/morseangel) | Python/Jupyter DNN, MIT | ML, not classical | Out of scope: the project wants a classical timing decoder, not a second ML model with a bundling/benchmarking profile like deepcw-engine's. |

**The classical adaptive algorithm** converges to the same thing across every non-ML candidate above (there is no single canonical paper): keep a running estimate of the dot length from recent short marks (or, per wb7fhc, of the dash length with dot = dash/3); classify each subsequent mark/space as a multiple of that estimate (dit ≈ 1, dah ≈ 3, intra-character gap ≈ 1, inter-character gap ≈ 3, word gap ≈ 7 — textbook values; legacy's `WriteCWID` actually puts 10 dots of silence on the wire for a word gap, see §8.4 step 5); keep updating the estimate so it follows the sender's actual speed. A C# port is a self-contained module of a few hundred lines (tone/envelope detection plus this classifier) — not a large undertaking, which is what tips build over adopt.

**Decision (final).** Build our own adaptive classical decoder (§8.4). Not fixed-timing (§1, §8.4 — `StationIdSettings.CwWpm` is user-configurable). Not ggmorse/ditdah (interop and packaging cost outweighs the benefit at this scope). deepcw-engine (AGPL-3.0-only), fldigi (GPL-3.0), and RSCW (unlicensed) are excluded from direct code reuse; the deepcw sidecar option above is unaffected by this section.

## 8. Part B — integration architecture

### 8.1 Where CW ID actually occurs (verified) and what that implies

- Legacy TX (`Main.cpp:7016-7027`): after the last image line, `OutputFSKID()` if FSK ID is enabled, then `OutputCWID()` (`sys.m_CWID == 1`) or `OutputMMV()`. `WriteCWID` (`sstv.cpp:2951-3003`) keys a single tone at `m_CWIDFreq` (default 1000 Hz, `Main.cpp:907`), dot length `m_CWIDSpeed+30` ms (default 40 ms; WPM default 28, `Main.cpp:904-905`), text default "DE %m" (`Main.cpp:906`), with a 250 ms leading silence for '@'.
- This port's encoder mirrors that order exactly: footer → FSK ID → CW segments (`AnalogFmSstvEncoder.cs:589-618`, `CwMorseGenerator.cs`), defaults in `StationIdSettings.cs` (`DefaultCwWpm = 28`, `DefaultCwToneFrequencyHz = 1000`, `DefaultCwText = "DE %m"`).
- Duration budget: "DE W1AW" is roughly 60 dot-units ≈ 2.4 s at 28 WPM (39.6 ms dot) and ≈ 6.7 s at 10 WPM; "DE W1AW/M" at 10 WPM approaches 9 s. FSK ID with NR/RST precedes it by ~1-2 s. So a **12 s post-image window** (cap 20 s, matching DeepCW's max) covers every realistic ID; make it a setting with that default.
- Therefore: CW ID is **in-band, same audio stream, positional after the image**. There is no need for an always-listening CW decoder in v1, and building one would compete for CPU with the SSTV decoder, trigger false decodes on SSTV tones and sync pulses, and be scope creep relative to "decode the CW ID". A general CW decoder pane is a separate future feature, not part of this plan.
- Assumption (not verified against any other SSTV software): other programs that send CW ID (MMSSTV itself, from which YONIQ forks) place it in the same post-image position. Operators occasionally key an ID by hand before or after; a manual "Decode CW from the last N seconds" command (§8.5) covers that without an always-on path.

### 8.2 Audio tap — reuse the existing fan-out, arm on `ModeDetected`, open at the true image end

- `SstvSessionService` already fans the capture stream out to four isolated handlers (`_decoderHandler`, `_waterfallHandler`, `_levelMeterHandler`, `_audioAutoSaveHandler`; subscribed at `SstvSessionService.cs:2013-2016`, each with its own try/catch and rate-limited logging, `:266-335`). Add a fifth, `_cwIdHandler`, in a new partial `SstvSessionService.CwId.cs` modeled on `SstvSessionService.AudioAutoSave.cs`.
- **The existing auto-save audio slice cannot be reused**: it closes at `transmissionLineCount + 2` lines (`SstvSessionService.AudioAutoSave.cs:29`, `ArmLocked` at `:317-335`), i.e. just after the last image line, *before* the FSK/CW tail. The CW window is a separate, smaller arm: on the same `ModeDetected` arm point compute the image-end sample count the same way (rows-per-transmission-line via `ColorEncoding`, not `ImageHeight` — the plan doc's own hard-won rule), then capture `[imageEnd, imageEnd + windowSamples]` into a pre-sized buffer, and hand it off. `AudioCaptureReset` (device/rate change, TX pause, file-decode entry) drops an open arm exactly as the audio slice does.
- **Window origin: the decoder's corrected image-start anchor plus the nominal image length — not "arm point + image length".** Two separate lateness sources were found and both are removed. (1) The auto-save close threshold adds `AudioCloseThresholdMarginLines` (= 2, `SstvSessionService.AudioAutoSave.cs:29`) to `transmissionLineCount` in `ArmLocked` (`:320-322`) to deliberately *over*-capture the image; reused as the CW origin it would be ~1.9 s late for PD290 (`SstvModeRegistry.cs:453`: 308 transmission lines of ~940 ms). The CW arm uses **no** margin lines. (2) More importantly, **`ModeDetected` itself is deferred**: for every non-AVT mode `Commit()` parks the match in `_pendingAnchorCorrectionMode` (`AnalogFmSstvDecoder.cs:4926-4933`) and `ModeDetected` is only raised from `FinalizeAnchorAndStartDecoding` (`:4959-4963`) once `TryResolveSyncAnchorCorrection` has `lineCount * pageWidthSamples` of audio past the provisional anchor, `lineCount` = 3 or 4 depending on mode and `RxBufferMode` (`:5014-5020`; the diagnostic hook at `:4718-4721` says the same in words: deferred "several lines … later"). So the arm callback runs ~3-4 transmission lines **after** the image started, plus up to one push chunk. Measuring the image length from the arm point would therefore open the window ≈ 3.75 s late for PD290 and ≈ 1.7 s late for Scottie 1 — worse than the 1.9 s margin error in (1), and enough to open *inside* a ~2.4 s "DE W1AW" at 28 WPM that begins ~1-2 s after the image (§8.1), or after it entirely.
  **Chunk-index invariant (states an assumption the design otherwise leaves implicit):** the handler determines a chunk's absolute pushed-sample index as `_pushedSampleCount - samples.Length` at the moment it runs — there is no other source for that index. This is only correct if `_cwIdHandler` observes `_pushedSampleCount` *after* it has been incremented for the current chunk, which in turn requires `_cwIdHandler(chunk)` to be subscribed/invoked after `PushSamplesToDecoder(chunk)` for the same chunk (`SstvSessionService.cs:2013-2016` subscription order, and `:2436`'s file-decode loop ordering, both become load-bearing on this point, not incidental). A handler-local running counter would drift by an arbitrary, unbounded amount instead and must not be used. **Second precondition, easy to miss:** `_decoderHandler` itself early-returns WITHOUT pushing when `_autoDetectPaused` is set (`SstvSessionService.cs:274-289`) — a period that includes exactly the time an open post-image CW window is waiting. A naive `_cwIdHandler` that still ran during that pause would receive chunks `_pushedSampleCount` was never incremented for, desynchronizing its own index math from the true arrival stream — and this case is NOT covered by the `DecodeRestarted`-drop rule below, since `SetAutoDetectPaused(true)` (`:452-465`) raises neither `AudioCaptureReset` nor `DecodeRestarted`. `_cwIdHandler` must therefore mirror `_decoderHandler`'s own `_autoDetectPaused` early-return exactly, and additionally drop any already-open arm when that state is entered (a chunk that was never pushed cannot be indexed against).
  **Decision (option (b) of the three below, with the correction term measured by the decoder rather than hardcoded).** The decoder already knows the exact quantity at the raise: `TotalSamplesReceived - _consumedSamples` (`AnalogFmSstvDecoder.cs:317`, `:338`; `_consumedSamples` is the corrected line-0 anchor by then, `:5109`) — and `FinalizeAnchorAndStartDecoding` uses precisely that anchor plus `totalTransmissionLines * LineDurationMs` as this image's own audio extent (`_afcBoundSample`, `:4953-4954`), i.e. the same origin the CW window wants. Expose it as a read-only `ISstvDecoder.AnchorLagSamples` (int; `TotalSamplesReceived - _consumedSamples` captured immediately before the `ModeDetected` raise at `:4963`; 0 before any lock; `RestartableSstvDecoder` delegates to `_inner` exactly like `BufferedSampleCount`, `:1507-1513`), read *inside* the `ModeDetected` callback — the same read-in-callback contract `ReceptionSequence` already has. The CW arm then computes, in the session's own pushed-sample coordinates (`PushSamplesToDecoder` is the single funnel for live and file audio, `SstvSessionService.AudioAutoSave.cs:166`; add a `long _pushedSampleCount` beside `_pushEpoch`, incremented by the chunk length *before* `_decoder.PushSamples` so the count includes the chunk in flight when the synchronous callback runs): `imageStart = _pushedSampleCount - AnchorLagSamples`; `windowOpen = imageStart + transmissionLineCount * LineDurationMs * sampleRate` (rows-per-transmission-line via `ColorEncoding`, the plan doc's own hard-won rule, `:314-322`); `windowClose = windowOpen + windowSamples`. The window is in the future at arm time for the anchor-correction path (an image is hundreds of lines, the lag is ~4), so **no pre-roll or backfill buffer is needed** there: the handler appends only samples whose pushed index is ≥ `windowOpen`, slicing the straddling chunk, and hands off at `windowClose`. This is not an absolute guarantee for every raise path — a header-search-derived anchor (`Commit` at `:5308`/`:2833`, outside the deferred-correction path) can in principle report a larger lag — but the design degrades gracefully rather than needing a fallback. Direction check: `imageStart = _pushedSampleCount - AnchorLagSamples`, so a LARGER lag makes `imageStart` (and therefore `windowOpen`) EARLIER, not later — the window opens sooner, landing partway into the tail of image audio rather than after it. This is still bounded and safe: the extra image audio it captures still fails step 4's own timing guard (real SSTV sync pulses are single-length, not the 1:3 dit/dah ratio step 4 requires, so they're rejected there even if step 1's tone-find locks onto one), so the realistic worst case is a missed or truncated CW ID, never a crash or a wrong-reception splice. Two implementation guards this depends on, both worth stating explicitly rather than assuming: `_pushedSampleCount` must be monotonically increasing for the whole session lifetime (never reset by `HandleAudioCaptureReset` — a reset should drop the open arm, per the `AudioCaptureReset` rule above, not zero the counter that other in-flight math relies on), and `imageStart`/`windowOpen` must be clamped to `≥ 0` before use, since a lag figure exceeding the session's own pushed-sample count so far (a raise-path corner case, not the common one) would otherwise produce a negative window bound. Residual origin error is the slant/clock error only — `FinalizeAnchorAndStartDecoding`'s own comment bounds it at ~0.1 % of image length (`:4942-4947`), ≤ ~0.3 s for PD290 and sub-100 ms for everything shorter — which is smaller than the ≥ 250 ms gap legacy always leaves before the first CW element (`WriteCWID`'s leading '@' silence, §8.1) even with FSK ID off, and far smaller than the 1-2 s FSK-ID span with it on. **§8.4 step 1's safety claim is therefore restated, not lost:** the window can contain at most that slant-bounded tail of image audio (a continuous, unkeyed SSTV tone), never the 3-4 lines the arm-relative origin would have exposed; step 1's "no keying bimodality → reject" check is what makes even that tail harmless. AVT (`Commit()` finalizes immediately, `:4927-4929`) simply reports a small lag; the same formula applies.
  *Why not (a), a new `ISstvDecoder.ImageCompleted` event from `EndOfImage()` (`:3797`)* — this was the alternative §8.2 rejected in an earlier draft and it was re-examined on purpose: it is still rejected, for a sharper reason than review weight. `EndOfImage` runs at the *decode* position, which trails the *pushed* position by the same buffered-lines lag (`:4718-4721`), so the event would still have to carry a lag figure **and** the Application would need a backfill ring for the samples already pushed past the true end — i.e. it needs everything option (b) needs plus a new event, a payload type, and a raise-site audit of `EndOfImage`'s abandon/auto-stop/`resumeFrom` callers (`:2016`, `:2028`, `:3712`; declaration `:3863`) to fire only on natural completion. (b) adds one read-only property and no new event.
  *Why not (c), seeding from the auto-save pre-roll ring* — the ring is only written while `_autoSaveAudioEnabled` is true (`SstvSessionService.AudioAutoSave.cs:255-259`), so the CW path would silently depend on an unrelated user setting or force the ring on for everyone; and a backfilled window that starts *before* the true end by design would put 3-4 lines of SSTV tones (1500-2300 Hz, 1200 Hz sync) inside the tone search of §8.4 step 1 — exactly the origin-pulled-earlier hazard flagged in review. The lag is knowable exactly; guessing around it with a 10 s ring is the wrong tool. Off-scope, one line: §8.5's manual "last N seconds" command already reads that ring and inherits the same auto-save-only gating; note it there when B-P6 is planned.
- **`DecodeRestarted`: drop the open arm, nothing else.** `ReceptionSequence` is bumped in exactly two places, both inside `ModeDetected` handling (`AnalogFmSstvDecoder.cs:4962`, `RestartableSstvDecoder.cs:1811`) — never by `DecodeRestarted`. Every `DecodeRestarted` raise site (`AnalogFmSstvDecoder.cs:2019` abandon, `:2841` re-sync, `:3708` auto-stop, `:3777` mid-image re-lock) leads to one of two outcomes: the reception re-`Commit`s and fires a **fresh** `ModeDetected` with a **new** sequence, or it is abandoned for good. Re-arming at restart time would double-arm in the first case (a stale restart-time arm plus the one the next `ModeDetected` naturally creates) and, in the second, anchor a 12 s capture to a dead reception whose eventual `CwIdDecoded` A5's guard drops — wasted work either way. The auto-save subsystem does exactly this and only this: `OnAudioAutoSaveDecodeRestarted` (`SstvSessionService.AudioAutoSave.cs:209-231`) closes the armed slice on a later-epoch restart and has no re-arm logic of its own; re-arming happens when the next real `ModeDetected` fires. `SstvSessionService.CwId.cs` mirrors that precisely — subscribe to `ISstvDecoder.DecodeRestarted`, record `_pushEpoch` at arm time, ignore a same-epoch restart (it refers to the older reception the arm already accounted for, `:57`, `:164-200`), and on a later-epoch restart **drop** the open CW arm. No re-arm path exists in the CW partial at all.
- The decode itself runs on `Task.Run`, never on the drain thread; the result event is raised from that continuation wrapped in try/catch — the same contract `AudioSliceReady` documents (`ISstvSessionService.cs`, "raised only AFTER the background encode+write completes, never on the audio drain thread").
- **Bulk file decode (`DecodeFromFileAsync`) must fan out to `_cwIdHandler` explicitly.** The file-decode loop (`SstvSessionService.cs:2436-2438`) calls exactly three targets — `PushSamplesToDecoder` / `_waterfallHandler` / `_levelMeterHandler` — and *deliberately* omits `_audioAutoSaveHandler` (the file is already the audio; capturing it again is pointless, and the auto-save partial additionally gates itself on `_fileDecodeInFlight`). A CW handler cloned from the auto-save partial would inherit both exclusions and receive **zero samples** during a `.wav`/`.mmv` re-decode. B-P2 must therefore (a) add `_cwIdHandler(chunk)` as a fourth call in that loop, and (b) *not* copy the `_fileDecodeInFlight` early-return into the CW arm/restart handlers. "Re-decode a recording and get its CW ID" (§10's golden-vector row and the manual last-N-seconds command in §8.5) depends on this; the Application test in §10 must include a file-decode case that asserts `CwIdDecoded` is raised.
- **End-of-file: flush a window that has opened, drop one that has not — before live capture resumes.** `DecodeFromFileAsync` calls `StopReceivingLockedAsync` at entry (`SstvSessionService.cs:2400` → `HandleAudioCaptureReset`, `:2213`), which drops any *live* CW arm, but its inner `finally` (`:2443-2455`) calls `StartReceivingLockedAsync` (`:2449`), which re-subscribes the four `SamplesCaptured` handlers (`:2013-2016`) with **no** reset signal. A recording trimmed near the image end — the normal case for a fixture — ends before a 12 s window fills, so without an explicit step the arm would (i) never raise `CwIdDecoded` for the file and (ii) stay open into live capture, splicing microphone audio onto the file's samples in one decode. Rule: `SstvSessionService.CwId.cs` exposes `FlushOrDropCwArmForEndOfFile(bool completedNormally)`, called from **inside the existing inner `try` block** (`:2445`), not before or after it — placing the call before that `try` (e.g. directly in the `finally` at `:2443`) risks a throw that skips `_rxTransitionGate.Release()` (`:2452-2455`), which would permanently deadlock every subsequent RX transition; calling it inside the existing `try` keeps it covered by the same exception handling that already protects `StartReceivingLockedAsync`. `completedNormally` is a local **initialized to `false`** and set to `true` only immediately after the `await Task.Run(...)` decode loop returns successfully — it is NOT derived from a catch block: wrapping `OperationCanceledException` in its own `catch` to explicitly set `false` risks silently swallowing a cancellation that `DecodeFromFileAsync` currently propagates to its own caller, which this change must not alter. Init-false-then-set-true-on-success achieves the same result without adding a new catch clause. If the file ended normally and the window's `windowOpen` point was reached, the partial capture is handed off exactly as a full one would be (`ClassicalCwDecoder` already has to handle short windows — a window with under ~1 s past `windowOpen` reports "no tone", `Confidence = 0`); if `windowOpen` was never reached (file ended inside the image), or the decode was cancelled/faulted, the arm is dropped and logged (`CwIdWindowDroppedAtEndOfFile(receptionId, reason)`). Flush, not drop, is chosen for the normal-completion case because a fixture that ends right after the CW ID is the *expected* shape of "re-decode a recording", and dropping it would make the feature useless for exactly that. §10's Application row carries the matching tests.

### 8.4 v1 backend — adaptive classical timing decoder (own code, no license question)

Scope is deliberately narrow: one machine-keyed tone, **unknown speed that is constant within one ID**, 5-20 s window, known text shape. The speed is *estimated from the received marks*, never assumed from our own settings.

**Fixed-timing was considered and rejected.** Hardcoding the classifier to this port's 28 WPM default (`DefaultCwWpm`, `StationIdSettings.cs:25`) would have removed steps 4-5 below, but `StationIdSettings.CwWpm` (`:65`) is a nullable, user-editable Options setting — any operator, including another Scanline Studio user, can change it, and legacy YONIQ/MMSSTV exposes `CWIDWPM` the same way (`Main.cpp:904-905`). A fixed-28-WPM decoder would decode only stations that left the default alone; RSCW's own documentation (§7.1) describes precisely this failure mode for non-adaptive decoders. The adaptive version costs one running estimate and is what every surveyed classical decoder does (§7.1); wb7fhc-cw-decoder's dash-duration tracking is the reference shape.

Steps, each independently unit-testable:

1. **Tone find**: magnitude spectrum of the window (reuse the existing FFT in `Core.Sstv` only if it is exposed; otherwise a small Goertzel sweep) across the **full 100-3000 Hz range** at ~10 Hz steps; take the top-N candidate peaks by magnitude (N ≈ 3-5), run the FULL pipeline (steps 2-4, scored by step 7) independently on each candidate, and return the **best-scoring** candidate's own decode result — not simply the first candidate whose keying pass happens to succeed. Report "no tone" only if every candidate scores below a floor. The band is 100-3000 Hz because that is exactly what `CwToneFrequencyHz` lets any Scanline Studio operator set (`OptionsWindowView.axaml:833`, `NumericUpDown Minimum="100" Maximum="3000"`) — the same "another operator changed the setting" argument that rejected fixed 28 WPM applies to the tone. The narrower 400-1200 Hz band that appeared in an earlier draft was DeepCW's own spectrogram band (§6) and has no bearing on a classical decoder searching for an unknown user-configured tone. **Real risk this ranking exists to close, and why bimodality alone doesn't close it**: the window's origin is the true image end (§8.2), so the FSK ID (legacy `sstv.h:706-707`: `FSKINTVAL` = 22 ms/symbol, `FSKSPACE` = 2100 Hz; the 1900 Hz mark tone is an inline literal at `sstv.cpp:2946`) can fall INSIDE the window when FSK ID is enabled, not just a slant-bounded SSTV tail. FSK ID is frequency-SHIFT keyed (continuous tone alternating between 1900 Hz and 2100 Hz), not on/off keyed — but viewed through a Goertzel filter centered on EITHER of those two frequencies alone, it presents as a textbook-clean on/off envelope (present at that one frequency, absent when the signal shifts to the other), which passes step 3's bimodality check trivially; both the 1900 Hz mark bin AND the 2100 Hz space bin present this identical hazard, not just one of them. Its 22/44/66/88 ms run lengths also survive step 4's own guards uncomfortably often (≥6 marks easily met; k-means long/short ratio can land inside the accepted 2.2-4.0 band for plausible bit patterns). **The actual discriminator is step 4's own mark-length CLUSTER SEPARATION, not step 3's bimodality**: real CW occupies exactly two tight clusters (dit-length and dah-length, at a 1:3 ratio) with an empty gap between them; FSK ID's mark-run population is continuous across 1, 2, 3, 4+ symbol-length units with no such gap. Step 4 must reject a candidate when a material fraction of its marks falls in the gap between the two cluster centres, not just check the aggregate long/short ratio — that gap-occupancy check, combined with step 7's own timing-fit score, is what a per-candidate best-scoring selection is actually scoring on. A simpler minimum-total-on-time filter (reject short-total-mark-duration candidates) was considered and explicitly NOT adopted as the primary defense — it would risk rejecting genuinely short or fast real CW IDs, which is a worse failure than the one being fixed. A cheap, optional additional guard: when `FskStationIdDecodedInfo` has already fired for the current reception (Part A's own pipeline), demote any tone-find candidate within ±50 Hz of 1900/2100 Hz, since a real FSK ID was just confirmed present.
2. **Envelope**: Goertzel magnitude at the found tone over 5 ms blocks (bandwidth ~200 Hz), smoothed with a 3-block median.
3. **Keying detection**: threshold derived from a **bimodal (Otsu-style) split of the envelope restricted to the active-signal region**, not from fixed global percentiles. Rationale: a fixed 10th/90th-percentile midpoint assumes marks occupy a healthy fraction of the window, but "DE W1AW" at 28 WPM is ~2.4 s of mark time inside a 12 s window (~10% of samples — right at the 90th-percentile boundary) and under 6% at the 20 s cap or with a shorter ID, so the 90th percentile lands in noise and the threshold collapses toward the floor. Procedure: (i) coarse gate — find the contiguous region of the window whose envelope exceeds the median by a fixed SNR margin (the CW burst itself), padded by a few hundred ms; (ii) within that region only, compute the two-class Otsu threshold on the envelope histogram (maximizes between-class variance; converges to the mark/space midpoint regardless of duty cycle); (iii) apply ±10% hysteresis around it to avoid chatter; (iv) run-length encode into mark/space intervals. If no region passes (i), or the two Otsu classes are not separated by at least the SNR margin, report "no tone". Note for the test suite (§10): `CwMorseGenerator` fixtures are ~50% mark/space and would pass a naive percentile threshold — the unit tests must include a **sparse-window** case (a short ID at 28 WPM padded with 10+ s of silence/noise) to exercise this step.
4. **Speed estimate (adaptive)**: seed the dot length from the window's mark lengths (k-means with k=2; dot = short-cluster centre, cross-checked against long-cluster/3 as wb7fhc does with the dash); reject the window if the long/short ratio is outside 2.2-4.0, there are fewer than ~6 marks, **or a material fraction of marks falls in the gap between the two cluster centres** (the FSK-ID discriminator step 1 depends on — real CW's two clusters are tight and well-separated at a 1:3 ratio; a signal whose mark-run population is smeared continuously across that gap, like FSK ID's 1/2/3/4-symbol-length runs, is not CW even if its aggregate long/short ratio happens to pass). Then, while walking the marks in order, keep a running dot estimate (exponential average over the most recent classified dits and dahs/3) so the classifier follows the sender's actual timing across the ID rather than a value fixed at the start — or from our settings. Search range **5-50 WPM**: 50 is the real ceiling — legacy's own input box accepts only 10-50 (`Main.cpp:14847-14851`, "PARIS 10 - 50 WPM") and this port's stepper has the same bounds (`OptionsWindowView.axaml:837`, `Minimum="10" Maximum="50"`); the floor is widened from 10 to 5 only to tolerate slow hand keying. **Accepted dot range must cover THREE distinct conventions, not just legacy's**: legacy's own integer-truncating formula (`sstv.cpp:2967`: `dot = speed + 30`; `Main.cpp:13742`: `speed = (int)((1110.0/WPM) - 30.0 + 0.5)`, `m_CWIDSpeed` is `int`, `ComLib.h:263`) gives 50 WPM → `(int)(-7.3) = -7` → dot = **23 ms**, 28 WPM → `(int)(9.6) = 10` → dot = **40 ms** (NOT 39 ms — the previous draft mis-truncated this one; 40 ms also matches §8.1 and §10, which both already state it correctly), 10 WPM ≈ 111 ms, 5 WPM → `(int)192.5 = 192` → dot = 222 ms. **This port's OWN encoder uses a DIFFERENT, deliberately undocumented-as-a-port formula**: `CwMorseGenerator.MillisecondsPerDotFromWpm(wpm) => 1110.0 / wpm` (`CwMorseGenerator.cs:47`, used by TX at `AnalogFmSstvEncoder.cs:617`) — a documented intentional deviation from legacy's truncating formula, per that method's own doc comment (`:38-45`), NOT the same computation as legacy's despite an earlier draft of this doc claiming otherwise. At `CwWpm = 50` (this port's own maximum), that formula gives a **22.2 ms** dot — below legacy's 23 ms floor. A decoder that only accepted 23 ms and up would fail to decode a fellow Scanline Studio operator transmitting at their own app's maximum supported speed, the exact bug class this whole adaptive-vs-fixed design already exists to avoid. Accepted dot range is therefore the widest span across all three conventions (legacy-truncated, this port's own generator, and textbook PARIS 1200/WPM) at each end: **≈22-240 ms**. Report the final estimate as `CwDecodeResult.Wpm`.
5. **Classification**: against the *current* running dot estimate: mark < 2 dot → dit, else dah; space < 2 dot → intra-character, < 5 dot → character gap, else word gap. The classification thresholds are the standard 1/3/7 with tolerance, but the **ideal gap values used for confidence scoring (step 7) must match what legacy actually emits**: `WriteCWID` writes `dot` of silence after every element (`sstv.cpp:2999`) and `dot*2` after every character (`:3002`), so the real inter-character gap is 1 + 2 = 3 dots; a space character writes `dot*7` and returns *without* the trailing `dot*2` (`:2988-2991`), so the real inter-word gap on the wire is the preceding character's 1 + 2 plus 7 = **10 dots**, not 7. Ideal values: intra-element 1, inter-character 3, inter-word 10.
6. **Lookup**: inverse Morse table. An undecodable mark/space pattern is **not** rendered as `?` — `?` is a real, decodable Morse character (`0xcc06` in the legacy table, `sstv.cpp:2957`). Instead each `CwDecodedCharacter` carries `bool IsUnknown` (with `Char = '\0'` and the raw dit/dah pattern string retained for the log); the `Text` string renders unknown characters as U+FFFD (`�`, which is not in the Morse alphabet and cannot collide) and applies a confidence penalty. `CwIdCallsignExtractor` treats any token containing an unknown as non-callsign.
7. **Confidence**: fraction of characters whose element and gap timings fall within ±25% of the ideal for the estimated dot — using the 1/3/10 ideals from step 5, so a genuine word gap is not penalized as a "too-long 7" — times a tone-SNR term. Expose per-character confidences so the UI can render low-confidence characters differently later if wanted.

Expected cost: trivially real-time (a few million multiply-adds per window). Known weaknesses, stated up front: hand-keyed or badly weighted CW, QSB inside the window, and two overlapping stations. None of these describe an SSTV CW ID from a station whose image just decoded.

### 8.5 Optional later backend — DeepCW sidecar (gated on §7)

- `ScanlineStudio.Cw.DeepCw` as an **optional project excluded from the default publish** (same idea as the Windows-only OmniRig module being optional): implements `ICwIdDecoder` by (a) band-limiting and decimating the window to 3200 Hz with a real anti-alias filter (do not copy the example's linear interpolation) — and skipping the sidecar entirely (classical result only) when the classical tone-find (§8.4 step 1) reports a tone outside DeepCW's 400-1200 Hz band, which it cannot decode, (b) writing a temporary 16-bit mono WAV, (c) launching the user-configured deepcw-engine runner (`python decode_morse.py --wav …` or the Node equivalent) as a child process with a timeout, (d) parsing stdout. Settings: runner path, model/metadata paths, timeout. Everything is async, logged, and failure falls back to the classical decoder's result.
- Spectrogram parameters must be read from the user's `model.onnx.json` at runtime if a direct ONNX Runtime path is ever chosen — never transcribed into this repository (they are part of the AGPL work).
- Benchmark before enabling by default: p95 wall time per 12 s window on the reference dev machine, and CER on the fixture corpus (§9) against the classical decoder. Only adopt as default if it wins on impaired fixtures without losing on clean ones — the same paired-evidence rule `decoder_quality_improvement.md` §4 applies to the SSTV decoder.
- A manual "Decode CW from the last N seconds" command (RX pane button, reads the last 20 s from the pre-roll ring the audio auto-saver already keeps, `SstvSessionService.AudioAutoSave.cs:59-65`) is the cheap way to cover hand-sent IDs and to let operators exercise the DeepCW backend on demand. Caveat to resolve when B-P6 is planned: that ring is written only while auto-save audio is enabled (`:255-259`), so the command either depends on that setting or needs its own always-on ring — the v1 window path (§8.2) deliberately uses neither.

### 8.6 Real-time vs buffered — cost and acceptability

Buffered is the right shape here: the CW ID is by definition after the image, so the earliest useful result is at window close (≤12 s after the last line) plus decode time (milliseconds classical; unmeasured but likely sub-second for DeepCW on CPU). The RX pane is not waiting on it for anything — the image is already saved. No streaming display, no partial-text rendering, no per-keystroke latency concerns. If a live "listening…" cue is wanted, a single boolean (`IsListeningForCwId`) toggled at arm/close is enough.

## 12. Items not recommended

- Bundling deepcw-engine's model, metadata, or example code in this repository or the default distribution (AGPL-3.0-only vs LGPL-3.0-or-later).
- A fixed-timing decoder hardcoded to our 28 WPM default: `StationIdSettings.CwWpm` is user-configurable (§1, §8.4), so it would fail on every station — Scanline Studio, YONIQ, MMSSTV or otherwise — whose operator changed the speed.
- Adopting ggmorse or ditdah via P/Invoke/FFI, or transcribing code from fldigi's GPL-3.0 CW modem (§7.1). Cross-reference their algorithms; do not link or copy them.
- Loading an AGPL decoder as an in-process plugin assembly; the plugin host does not exist and the licensing does not improve.
- Transcribing DeepCW's spectrogram parameters (`fft_length`, `hop_length`, band, normalization) into C# as constants — read them from the user's metadata file at runtime if that path is ever taken.
- An always-on, general-purpose CW decoder tap in v1: CPU contention with the SSTV decoder, false decodes on sync/VIS tones, and scope creep. Ship the post-image window; add a manual last-N-seconds command for hand-sent IDs.
- Letting a CW-derived callsign overwrite an FSK-decoded one, or auto-triggering QRZ lookups on any decode (the existing user-approved boundary: fill the field, no surprise network activity — `RxImagePaneViewModel.cs:1556-1563`).
- Introducing a toast/notification framework for the decode event; the row annotation, the session list, the log, and persistence cover every "did it decode?" question an operator can ask, including after the fact.
- Regenerating or "cleaning up" the legacy-captured CW fixture; it is the only evidence of the real on-air CW-ID shape.
- Making `CwIdRxEnabled` default-on before the classical decoder has been exercised on the legacy fixture and at least one OTA recording.

## 13. Final recommendation

Fix the FSK-ID foundation first — reception identity on the event, a log entry, and a source/time annotation on the card — then persist decoded IDs into the RX history so the Gallery and Log-QSO stop losing them, and keep a small session list so a second station never silently erases the first. Add CW-ID reception as a new bounded module driven by a post-image capture window, with a from-scratch **adaptive (variable-WPM)** classical decoder as the shipped backend — the speed is estimated from the received marks because `StationIdSettings.CwWpm` is user-configurable and other stations key at whatever speed they like — and the same card row, event shape, fakes, and test layers the FSK path already uses. Build it rather than adopt ggmorse/ditdah (interop and packaging cost at this scope), and reuse no code from deepcw-engine (AGPL-3.0-only), fldigi (GPL-3.0), or RSCW (unlicensed, non-adaptive). Treat deepcw-engine as an optional, user-installed, arm's-length sidecar at most, and only after an explicit licensing decision; do not bundle it, and do not let that decision block the classical v1.
