# UI

## Related

[[01-architecture]] (layering rule: UI never touches radio drivers directly) · consumes → `ScanlineStudio.Application` service interfaces from every other module · replaces `Main.cpp`/`Main.dfm` and the ~30 dialog `.cpp`/`.dfm` pairs (`Option`, `RadioSet`, `LogSet`, `MacroKey`, `ColorSet`, etc.)

## Purpose

Define the presentation layer: window/dialog structure, MVVM conventions, and how the UI stays fully decoupled from hardware and DSP internals per the CLAUDE.md rule "UI must never directly communicate with radio drivers."

## Framework and pattern

Avalonia UI 11, Fluent theme, strict MVVM via CommunityToolkit.Mvvm. Every view (`.axaml`) has exactly one view-model (`ObservableObject` or `ObservableRecipient`); views contain no code-behind logic beyond `InitializeComponent()` and purely visual concerns (e.g. a custom-drawn waterfall control's render loop). View-models depend only on `ScanlineStudio.Application` service interfaces, injected via constructor — never on `ScanlineStudio.Core.*` concrete types directly, which is the structural mechanism enforcing the layering rule from [[01-architecture]].

```csharp
public sealed partial class MainWindowViewModel : ObservableObject
{
    private readonly IRadioSessionService _radio;      // ScanlineStudio.Application, not ScanlineStudio.Core.Radio
    private readonly ISstvSessionService _sstv;
    private readonly ILogbookService _logbook;

    [ObservableProperty] private RadioStateViewModel? _currentRadioState;
    [ObservableProperty] private ImageViewModel? _receivedImage;

    public MainWindowViewModel(IRadioSessionService radio, ISstvSessionService sstv, ILogbookService logbook)
    {
        _radio = radio; _sstv = sstv; _logbook = logbook;
        _radio.StateChanges.Subscribe(s => CurrentRadioState = RadioStateViewModel.From(s));
    }
}
```

## Visual design direction

**The Industry design language (current, 2026-08-11)**: a technical "blueprint wireframe" look —
steel-blue accent (`#5980A6`) on a light, flat ground (`#F2F2F3`), square corners everywhere,
hairline (1px) borders instead of filled card backgrounds, `Barlow`/`Barlow Condensed` for
headings and body text, a bundled monospace (`DejaVu Sans Mono`) for every numeric/data readout,
and small "blueprint" corner-mark crosses on select bordered containers (group boxes, plot
frames) as the one deliberate decorative flourish. Built from a user-provided mockup
(`mockups/guidance/SSTV Console.dc.html` + its design-system CSS, `mockups/guidance/
LAYOUT-SPEC.md` for exact pixel/color/spacing measurements) and ported view-by-view across an
8-phase plan (fonts/tokens → atoms → chrome → Receive/Transmit/Gallery/Logbook tabs → Options
window → cleanup). Reference: a wireframe/schematic instrumentation aesthetic, not a specific
existing ham-radio app.

**This supersedes the previous "Aesthetic Directive"** (flat WSJT-X/fldigi-style utilitarian
chrome — gray Win32/Qt control faces, sunken monospace readout fields, filled card backgrounds,
`mockups/MainWindow_mock2.axaml`) in full. That directive's own implementation
(`Styles/Tokens.axaml`/`Cards.axaml`/`ChromeOverrides.axaml`) has been **deleted** — every view
now draws exclusively from `Styles/AtomsTokens.axaml` (color/spacing/font tokens) and
`Styles/Atoms.axaml` (the reusable control atom set: group boxes, chips, steppers, sliders,
segmented controls, tables, thumbnails, buttons, checkboxes, radios, etc. — see that file's own
numbered sections for the full inventory). The prior directive's borderless "raw SDR-
instrumentation" look (cuSDR64/Perseus/SDR++ reference) and its brief WSJT-X/fldigi-card
successor are both now historical only; neither is drawn from anywhere in the app.

**Explicitly banned** (unchanged across all three directives): rounded corners (`CornerRadius`
must be `0` everywhere — no exceptions); gradients; drop shadows; glowing backgrounds; excessive
whitespace; center-aligning layouts arbitrarily just to fill space.

**Two implementation gotchas migrated from session notes, not obvious from the code alone**:
`MainWindow.axaml`'s root `Window` needs an explicit `Background="{StaticResource IndustryBg}"` —
it silently relied on the old (now-deleted) `Cards.axaml`'s bare `Window` selector for this before,
which broke (whole page went pure white) the moment that file was removed; if a future full-app
background change is ever needed, this is the one place to change it, most of the page relies on
this root fill showing through uncovered areas. The Transmit tab's centre column (TX Image Editor)
is correctly blank until an image is selected (`MainViewModel.ActiveEditor` is null-until-populated
by design, confirmed working end-to-end) — not a bug if it comes up again.

**Layout & density rules** (unchanged in spirit, now expressed via the Industry token scale):
- **Extreme information density.** Screen real estate is at an absolute premium — tightly clustered
  controls, not spaced-out ones.
- **Minimal padding.** The Industry spacing scale (`AtomsTokens.axaml`'s `IndustrySpacing*`/
  `IndustryPadding*` resources) runs 2px (`Hairline`) to 11px (`Group`); 2-4px is the default for
  control-to-control spacing, larger values reserved for outer card/group padding, matching
  `mockups/guidance/PADDING-NORMALIZATION.md`'s derived table.
- **Grid-first geometry.** Rigid `Grid` layouts with precise row/column definitions, not loose flowing
  `StackPanel`/flex-box-style layouts for structural layout (a `StackPanel` for a short run of tightly
  packed controls inside one grid cell is fine; using it as the top-level layout mechanism is not).
  Reserve generous grid cells for raw data visualization (FFT spectrum, waterfall), but **not** at
  the expense of the main window's actual primary purpose — direct user correction, after seeing it
  running: "the main window should be for images, receiving, editing, tx-ing," not the waterfall.

**Typography & controls**:
- **Monospace for all data.** Frequency readouts, signal meters, numeric inputs, and any rapid-update
  display **must** use the bundled monospace font (`IndustryMonoFontFamily`, `DejaVu Sans Mono`) —
  prevents layout jitter on fast redraws. Unchanged in spirit from every prior directive.
- **Utilitarian standard text.** Labels/button text: small, crisp, legible (`Barlow`/`Barlow
  Condensed`, 9.5-12.5px depending on control). No oversized "eyebrow" text, no large headers —
  this is instrumentation, not marketing, with one narrow exception: small accent-colored
  monospace "kicker" labels (`IndustryKicker`) for section eyebrows, matching the mockup's own
  wireframe-schematic convention.
- **Hairline-bordered, strictly rectangular controls with explicit state feedback.** Buttons/
  toggles/chips show hover/pressed/checked/disabled state via border and fill swaps against a
  small fixed accent ramp (`IndustryAccent`/`600`/`700`/`800` + a handful of literal hover-mix
  tints), never a rounded "pill" — square corners and 1px hairline borders are the one
  least-negotiable rule carried through all three directives.

Custom-drawn controls (waterfall, spectrum trace) still carry the most visual weight and are
worth real design attention beyond a default `Canvas` fill. The waterfall's own color gradient is
a deliberate, previously-audited departure from strict Industry-palette fidelity (a 6-stop
SDR-style heatmap — WSJT-X/SDR++/GQRX convention — not the mockup's own flat single-tone plot;
see [[14-roadmap]]'s waterfall color/palette item and `WaterfallPalette.cs`), while the
surrounding chrome (plot frame border, controls, tabs, status fields) follows the same Industry
atoms as everywhere else.

## Main window layout

Legacy's actual main window is **paged**, not simultaneous: `Main.h` declares a real `TPageControl
*Page` with `TabSync`/`TabRX`/`TabHist`/`TabTX`/`TabTemp` tab sheets (`ComLib.h`'s
`enum { pgSync, pgRX, pgHist, pgTX, pgTemp }`), switched one-at-a-time via `Mmsstv->AdjustPage(...)`
— this corrects an earlier draft of this section that incorrectly claimed no legacy tab mechanism
existed at all (a `.dfm`-only grep miss — `.dfm` files are binary and were the only thing checked;
`Main.h`'s plain-text component declarations were not). This port does **not** replicate that
paging: this port's `Dock.Avalonia`-based layout (a fixed waterfall strip above an RX Image/RX
History tab group, TX Controls in a separate region, all simultaneously visible and resizable — the
waterfall was moved out of the RX Image/RX History tab group after real hands-on use showed a
tab-grouped waterfall took over the whole region when active, which no real SDR-instrument reference
this project's own Aesthetic Directive cites — SDR++/cuSDR64/Perseus — actually does) is a deliberate
modernization past legacy's one-view-at-a-time paging, not a "preserve behavior" concession — see
[[07-image-pipeline]]'s "Navigation: dockable panes, not legacy's paged main window" section for the
full reasoning (this is exactly the "old-fashioned" navigation pattern a real operator flagged
directly). [[07-image-pipeline]]'s new `RxHistoryPane` and inline stock/template picker extend this
same dockable-pane model rather than reintroducing paging or this port's own former dialog-based
`HistoryView`/`StockImageView` design (legacy's actual dialogs are `THistViewDlg`/`TStockView`).
Layout is implemented with Avalonia's `Grid`/`DockPanel`/
`Dock.Avalonia`, not a fixed-pixel canvas, so it can be resized/DPI-scaled cleanly, which the legacy
VCL fixed-layout forms could not do well.

**Pane visibility**: closing a dockable `Tool` pane (e.g. `RxHistoryPane`) has no built-in way back
without this — a minimal `View` menu (toggle items per closable pane, wired to Dock's existing tool
visibility, no saved-layout-across-restarts yet) is in scope alongside `RxHistoryPane`'s own
introduction, specifically to avoid a one-way-close trap. Full layout persistence across restarts is
explicitly deferred — [[12-settings]] doesn't have a dock-layout schema yet, and adding one is a
separate scoping decision, not a prerequisite for shipping the View menu. Known, accepted regression
from this deferral: legacy persisted which page was last active across restarts (`Main.cpp`'s
`ReadInteger("Window","MainPage",pgRX)`); every session now starts from the same default layout
regardless of what was open when the app last closed.

## Custom rendering

Waterfall and oscilloscope views are custom `Control`-derived Avalonia controls rendering via `DrawingContext` (or `SkiaSharp` custom draw if frame-rate profiling shows `DrawingContext` insufficient), fed by [[06-sstv-dsp]]'s `IWaterfallSource` — the view-model exposes only the already-computed magnitude-frame data; no FFT or filter math lives in `ScanlineStudio.UI`.

## Porting gotchas: reading `.dfm` files as reference

Legacy `.dfm` files are **binary**, not text (`Main.dfm` opens with a `FF 0A 00` binary-DFM header), and several contain embedded assets inline — `Main.dfm` has at least one bitmap (`BM` header) embedded mid-file, meaning some button/icon glyphs live *inside* the form resource, not only in `res/`. Treat `.dfm` files as needing a proper DFM-to-text conversion step (e.g. via a Delphi/C++Builder toolchain, or a third-party DFM parser) before anyone tries to "read the layout off the file" — grepping the raw bytes will miss both structure and embedded assets silently.

Even once converted to text, the coordinate/sizing values are **VCL-specific and not portable as numbers**: `Font.Height` is stored negative (pixel height, not point size), forms carry `PixelsPerInch = 96` plus `Scaled`/`DesignSize` properties that interact with VCL's own DPI-scaling model. Copying these numbers directly into Avalonia `Grid`/`DockPanel` layouts will misplace controls, because Avalonia's default font metrics and DPI model don't match VCL's 1:1. Use `.dfm` files as a reference for *which controls exist and their rough relative arrangement*, not as a source of exact pixel values to transcribe.

## Theming

Light/dark theme support using Avalonia's `FluentTheme` variants, user-overridable (settings UI not built yet) — a straightforward modernization over the legacy fixed VCL look, in line with the "Modern UI" design goal in [[00-project-overview]]. **Defaults to Light explicitly**, not OS-preference-follow (`App.axaml`'s `RequestedThemeVariant="Light"`) — a direct user correction after seeing the app default to dark on a dark-OS-theme machine; supersedes an earlier "follow OS preference by default" draft of this line.

## Testing

View-models are tested headlessly (no window shown) via Avalonia's headless test platform + xUnit: construct a view-model with faked `ScanlineStudio.Application` service interfaces, drive property/command changes, assert observable state — see [[13-testing]] for the full strategy. Visual/layout regressions are out of scope for automated testing and rely on manual verification per release.
